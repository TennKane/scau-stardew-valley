## 一、方案总览

### 核心流程

```
用户打开小程序 → 摄像头取景 → 对准地标 → 
  本地轻量模型识别(毫秒级) →
    ├─ 置信度 > 0.85 → 打卡成功 + 星露谷动画
    ├─ 0.5~0.85 → 上传云端二次确认
    └─ < 0.5 → 提示用户调整角度/靠近
→ 存入数据库 → 更新图鉴/进度
```

### 功能模块

| 页面 | 功能 |
|------|------|
| **相机页** | 全屏摄像头 + 悬浮识别提示 + 打卡动画 |
| **校园地图** | 像素风地图，标记已/未探索区域 |
| **图鉴页** | 收集到的地标卡片，星露谷风描述 |
| **任务页** | 每日/主线/限时任务 + 进度 |
| **个人页** | 徽章、排行榜、兑换记录 |

## 二、后端到底需不需要？

**结论：需要，但不能只用传统后端。**

微信小程序有这些硬性约束，导致**纯前端方案不可行**：

| 约束 | 影响 |
|------|------|
| **主包 ≤ 2MB** | 装不下任何机器学习模型（TFLite 模型最小 ~3MB） |
| **分包 ≤ 8MB** | 模型只能放 CDN 按需下载，不能随代码发布 |
| **本地存储 ≤ 200MB** | 模型 + 特征数据库 + 用户数据撑不了多久 |
| **无法保真传帧** | `onCameraFrame` 返回的 RGBA 数据不可直接上传为图片 |
| **无用户身份** | `wx.login` 必须结合后端才能获取 openid |
| **无防篡改** | 纯前端打卡可被脚本伪造 |

**所以后端承担三件事**：

1. **身份认证**（WeChat login → JWT）
2. **模型推理**（云端兜底识别 + 防作弊）
3. **数据持久化**（打卡记录、图鉴进度、排行榜）

## 三、推荐技术架构

### 总架构图

```
[微信小程序] ←→ [WeChat Cloud Base] ←→ [第三方AI服务]
     │                    │
     │                    ├─ Cloud Functions (Node.js)
     │                    ├─ Cloud Database (MongoDB-like)
     │                    └─ Cloud Storage (图片/模型文件)
     │
     └── 本地: TFLite 轻量模型 + 特征缓存
```

### 为什么推荐 WeChat Cloud Base（微信云开发）

之前"账本"和"Remember"项目用了 Next.js + Vercel + Turso，但这个项目的场景不同：

| 对比项 | 之前项目 | 本项目 |
|--------|---------|--------|
| 平台 | Web → 任何浏览器 | 微信小程序专用 |
| 用户认证 | next-auth | 微信 login + cloudbase |
| 部署 | Vercel (海外) | **需要ICP备案** 或 云开发免备案 |
| 实时性 | 低 | 中（需快速识别反馈） |
| 文件存储 | 不需要 | **大量图片** 需存储 |

**微信云开发的独特优势**：
- **免 ICP 备案**：云开发的默认域名 `tcb.com` 已被微信白名单，这是大学项目最大的省心事
- **免运维**：学生项目不用管服务器
- **微信生态集成**：登录只需 3 行代码，无需额外鉴权
- **足够用的免费额度**（见后文成本分析）

### 如果不走微信云开发

也可以用独立后端：

```
[微信小程序] ←→ [阿里云 ECS / 腾讯云轻量] ←→ [PostgreSQL / MySQL]
                    │
                    └── [Nginx + Node.js + Docker]
```

但需要：
- 购买域名 → ICP 备案（1-2 周审核）→ 配置 HTTPS
- 维护服务器（学生项目容易烂尾）
- 微信小程序的 request 域名必须备案白名单

**建议**：MVP 先用云开发，如果后续功能膨胀到云开发不够用，再切独立后端。

## 四、视觉识别方案详解

这是整个项目的**核心技术挑战**。以下是几个可行方案，按推荐优先级排列。

### 方案一：轻量特征匹配（推荐 MVP）

**原理**：不训练分类模型，而是用预训练特征提取器 + 特征向量相似度匹配。

#### 流程

```
预处理阶段（后台）：
  每个地标拍 10-20 张照片
  → MobileNet V2（去掉最后一层）提取 1280 维特征向量
  → 存入数据库

运行时（小程序端）：
  摄像头取帧 → TFLite 跑 MobileNet V2 → 1280 维向量
  → 与本地缓存的地标特征做余弦相似度
  → 最高分 > 阈值 → 命中
```

#### 优点
- **无需训练**：用 ImageNet 预训练的 MobileNet V2 即可
- **新增地标 0 成本**：拍几张照 → 提特征 → 配布，不用重新训练
- **模型通用**：MobileNet V2 是标准模型，TFLite 格式 3.7MB
- **离线可用**：特征库下载到本地后可离线识别

#### 不足
- 对光线/角度变化敏感（可以通过数据增强缓解）
- 极端相似的地标可能混淆（比如两栋风格相同的教学楼）

#### 工作量

| 事项 | 难度 | 时间估算 |
|------|------|---------|
| 采集地标照片 | ⭐ | 半天（每个地标不同角度/光线拍 20 张） |
| 编写特征提取脚本（Python） | ⭐⭐ | 1 天 |
| 小程序集成 TFLite | ⭐⭐⭐ | 2-3 天（需踩 WeChat 的 TFLite 坑） |
| 特征比对逻辑 | ⭐⭐ | 1 天 |

### 方案二：迁移学习分类器（准确率更高）

**原理**：在 MobileNet V2 基础上，用地标照片 fine-tune 一个分类器。

#### 区别

| | 特征匹配（方案一） | 分类器（方案二） |
|---|---|---|
| 模型大小 | 3.7MB（特征提取器） | 5MB（特征提取 + 分类头） |
| 新增地标 | 加照片 + 提特征，即刻生效 | 需要重新训练 + 重新部署模型 |
| 准确率 | 一般 | 较高 |
| 实现复杂度 | 低 | 中 |

**建议**：MVP 先用方案一，等地标数量稳定后转方案二提升体验。

### 方案三：云端推理兜底

两种场景需要云端：

1. **本地模型置信度不足**（0.5-0.85）：上传帧到云函数 → 用更强模型（EfficientNet 或 ViT）推理
2. **防作弊抽查**：随机 10% 的打卡要求云端复核

云函数运行 TFLite / ONNX Runtime，用 Python 或 Node.js 均可。

## 五、Serverless 架构设计

### 数据模型

```
users: {
  _id, openid, nickname, avatar,
  badges: [],           // 已获得徽章 ID 列表
  checkin_count: 0,
  last_checkin: Date,
  createdAt: Date
}

landmarks: {
  _id, name, category,                 // 分类：建筑/雕塑/景观
  description,                         // 星露谷风描述
  stardew_description,                 // e.g. "知识的远古祭坛"
  feature_vector: number[],           // 1280 dims (可存到单独 collection)
  thumbnail_url,
  season_hint: string[],              // 春/夏/秋/冬 特殊提示
  position: { lat, lng },             // 可选，用于地图标注
  difficulty: 1-5,                    // 难度，影响分数
  hints: string[]                     // 线索（由浅到深）
}

checkins: {
  _id, user_id, landmark_id,
  photo_url,                          // 云存储 URL
  recognition_method: "local"|"cloud"|"manual",
  confidence: 0.0-1.0,
  created_at: Date
}

badges: {
  _id, name, icon, description,
  requirement: { type, count }        // e.g. {type:"checkin", count:5}
}

tasks: {
  _id, title, description,
  type: "daily"|"main"|"seasonal",
  requirement: { action, target },
  rewards: string[],                  // 奖励徽章 ID
  start_date, end_date
}
```

### API 接口

云函数（每个独立部署，按需计费）：

| 接口 | 方法 | 说明 | 触发频率 |
|------|------|------|---------|
| `login` | 自动 | WeChat 登录换取 JWT | 每次打开 |
| `recognize` | POST | 上传帧数据，返回识别结果 | 每次打卡尝试 |
| `checkin` | POST | 确认打卡，存图存记录 | 每次成功打卡 |
| `landmarks` | GET | 地标列表 | 低频 |
| `progress` | GET | 用户进度 | 每次打开 |
| `leaderboard` | GET | 排行榜（学院/个人） | 低频 |
| `tasks` | GET | 任务列表 | 每次打开 |
| `claim` | POST | 领取奖励 | 低频 |

### 为什么不用 Vercel + Turso

- **Vercel 在中国大陆没有节点**，延迟 ~200ms，拍照打卡等反馈体验很差
- **Turso 与微信小程序**：Turso 的 HTTP API 可以用，但域名需 ICP 备案
- **如果 ICP 备案不是问题**：Vercel Edge Functions + Turso 也是可行方案，与已有技术栈一致

## 六、成本计算

### 场景假设

- **用户量**: MVP 阶段 500-1000 人（一个年级/学院）
- **活跃用户**: 200 人/天
- **打卡次数**: 每人每天约 3 次（含失败尝试）
- **图片存储**: 每次成功打卡存 1 张图 (~200KB)

### 微信云开发成本

| 项目 | 免费额度 | MVP 用量 | 月费 |
|------|---------|----------|------|
| **云函数调用** | 200,000 次/月 | 200人 × 30天 × (10次打开+3次打卡) ≈ 78,000次 | **¥0** |
| **云函数资源** | 200,000 GBs/月 | ~30,000 GBs | **¥0** |
| **数据库** | 2 GB 存储 / 10,000,000 读 / 1,000,000 写 | << 免费额度 | **¥0** |
| **云存储** | 5 GB 存储 / 50,000 下载 / 100,000 上传 | 200人 × 30天 × 1图 × 200KB = 1.2GB | **¥0** |
| **CDN** | 5 GB/月 | ~1-2 GB | **¥0** |

**静态资源额外**：
| 项目 | 费用 |
|------|------|
| 像素风 UI 资源（图片/音效） | 自行设计 |
| TFLite 模型文件托管 | 放云存储 CDN，纳入免费额度 |

**合计：¥0/月**（MVP 阶段完全在免费额度内）

### 如果使用独立后端

| 项目 | 规格 | 月费 |
|------|------|------|

### 可选额外成本

## 七、绕过微信小程序限制的替代路线

如果你不想深度绑定微信生态（或嫌备案麻烦），还有一个路线：

### 替代方案：PWA + Web
```
[Next.js PWA] ←→ [Vercel + Turso + UploadThing]
      ↑
 手机浏览器打开 → 添加到主屏幕
      ↓
 使用 getUserMedia API 调用摄像头
```

| 对比 | 微信小程序 | PWA |
|------|-----------|-----|
| **用户获取** | 扫码即用 | 需浏览器打开 + 添加桌面 |
| **推送通知** | 微信模板消息 | 需 Service Worker |
| **支付** | 微信支付 | 微信支付 H5 |
| **备案** | 仍需（不稳定的 302 方案） | 需要 |
| **开发体验** | 微信开发者工具（烂） | Next.js（爽） |
| **社区** | 微信封闭生态 | 开源生态 |
| **审核** | 微信审核（1-7 天） | 无审核 |

**推荐：先做 PWA 原型验证，再转小程序**。

这样做的好处：
1. 用你熟悉的 Next.js 快速搭建完整功能
2. 验证用户是否真的喜欢这个玩法
3. 小程序审核需要齐全材料，先做 Web 版不耽误
4. 核心逻辑（识别、打卡、图鉴）两个平台可以复用

## 八、MVP 启动计划

### 阶段一：技术验证（1 周）

```
目标：跑通 "摄像头取帧 → 识别 → 打卡成功" 全链路

1. 拍照采集 5 个地标各 20 张照片
2. 跑通 MobileNet V2 特征提取脚本
3. 写一个简单的 HTML 页面验证摄像头 + 特征匹配（Web 端先试）  
4. 确认阈值和准确率是否可用
```

### 阶段二：小程序 MVP（2-3 周）

```
1. 初始化云开发环境 + 数据模型
2. 相机页：取景 + 帧提取 + TFLite 推理
3. 打卡成功动画与记录存储
4. 图鉴页：展示已解锁地标
5. 用户登录 + 个人进度
```

### 阶段三：游戏化（2 周）

```
1. 地图页（像素风手绘）
2. 任务系统（每日/主线）
3. 徽章与排行榜
4. 音效与动效打磨
```

### 阶段四：推广运营

```
1. 新生入学周推广
2. 与食堂/文创店谈奖品兑换
3. 反馈数据迭代
```

## 九、与已有项目的技术复用

之前项目（Remember / 账本）可以复用的部分：

| 可复用 | 说明 |
|--------|------|
| **Tailwind 设计感觉** | 色板、字体、圆角系统可迁移到小程序 |
| **数据建模思路** | 数据库 schema 设计方法论 |
| **构建工具经验** | `npm run build` 每层验证的习惯 |
| **Turso/Drizzle** | 如果走独立后端路线可直接复用 |

**不可复用**的部分：
- Next.js / React → 小程序 WXML（除非用 Taro 跨端框架）
- Vercel 部署 → 云开发部署
- next-auth → 微信登录

如果希望尽可能复用技术栈，可以考虑 **Taro** 框架（React 语法 → 编译到微信小程序），但 Taro 本身也是个坑，建议小程序 MVP 用原生开发，稳定后再考虑跨端。
